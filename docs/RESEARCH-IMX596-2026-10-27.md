## 0. 结论速览

**可以做，而且比原有判断容易得多。** 旧文档 `FRONTCAM-2026-10-27.md` 的两个核心前提——"公开渠道没有 IMX596 的 Linux 驱动"和"拿不到初始化寄存器表"——**都已被推翻**。

| 项 | 结论 | 置信度 |
|---|---|---|
| 有没有现成 IMX596 Linux 驱动 | **有**，而且就是**同一台 liuqin** 的 mainline V4L2 驱动 | 已确认 |
| 有没有现成寄存器表 | **有，两份独立来源**（Qualcomm 侧 vendor 提取 + MediaTek 官方内核树） | 已确认 |

## 3. 现成驱动盘点

### 3.1 ★ 精确同设备实现：`Seeker0472/liuqin-nixos`

- 仓库：<https://github.com/Seeker0472/liuqin-nixos>（描述：*NixOS support for Xiaomi Pad 6 Pro (liuqin)*）
- 相关文件（实测下载成功，本地副本见附录 A）：

| 文件 | 大小 | 内容 |
|---|---|---|
| `pkgs/kernel/patches/0012-liuqin-camera-core.patch` | 87 354 B | DT + `qcom-liuqin-sensors.c` + camss sm8475 资源 |
| `pkgs/kernel/patches/0013-liuqin-camera-tuning.patch` | 57 500 B | S5KJN1 vendor 模式表 / GT9764 VCM |
| `pkgs/kernel/patches/0021-liuqin-camera-orientation.patch` | 1 261 B | DT `orientation`（前摄 = 0） |
| `pkgs/libcamera-af/tuning/imx596.yaml` | 1 407 B | 软 ISP tuning（blackLevel / AWB / CCM） |
| `pkgs/libcamera-af/0007-sensor-helpers.patch` | 3 491 B | `CameraSensorHelperImx596` |
| `docs/TODO/CAMERA-MAINLINE.md` | 14 108 B | 现状、硬件速查表、坑位 |

**驱动结构**（与"每颗 sensor 一个 .c"不同，它是表驱动的多 sensor 单驱动）：

```
static const struct cci_reg_sequence imx596_init[]      // ~365 条
static const struct cci_reg_sequence imx596_mode_0..3[]  // 每模式 ~76 条
static const struct cci_reg_sequence imx596_stream_off[] / imx596_stream_on[]
static const struct liuqin_mode   imx596_modes[]
static const struct liuqin_sensor_desc imx596_desc       // lanes/bus code/link freq/reg 映射
{ .compatible = "sony,imx596", .data = &imx596_desc }
```

`imx596_desc` 关键字段（原文）：

```c
.name = "imx596",
.lanes = 4,
.mbus_code = MEDIA_BUS_FMT_SBGGR10_1X10,
.link_freq = 678400000ULL,
.link_freq_menu = { 678400000, 1100000000, 549000000, 2196000000 },
.chip_reg = CCI_REG16(0x0016), .chip_id = 0x0596,
.vts_reg = CCI_REG16(0x0340),
.exposure_reg = CCI_REG16(0x0202),
.again_reg = CCI_REG16(0x0204), .again_min = 0, .again_max = 1008,
```

`imx596_modes[]`：

| # | 宽×高 | hts | vts |
|---|---|---|---|
| 0 | 5184×3904 | 7288 | 9975 |
| 1 | 2592×1952 | 4644 | 6302 |
| 2 | 2592×1472 | 4644 | 6302 |
| 3 | 2592×1472 | 4644 | 3151（高帧率） |

**它记录了 3 个真实踩坑点，直接省掉我们的调试时间**（`CAMERA-MAINLINE.md` + patch 注释）：

1. **stream-on 必须 16 位写**：vendor 容器里是 `0x0100 = 0x0103`（即 `0x0100=0x01, 0x0101=0x03`）。用 8 位写只把 `0x03` 写进 mode-select，"STREAMON 成功但永远没有数据"。
2. **link freq 必须是 678.4 MHz**：用 1.10 GHz 默认值会让 CSIPHY 失谐约 60%，同样表现为"能推流、收不到数据"。
3. **色彩是 BGGR**，不是 RGGB（最初按 RGGB 做，红色目标出蓝色）。

**许可与合规**（`NOTICE` 原文要点）：仓库整体 MIT，`pkgs/kernel/patches/*.patch` 为 GPL-2.0-only；寄存器表"从小米/高通二进制解码而来"，**源容器 `com.qti.sensormodule.*.bin` 未入库**；其立场是"寄存器值是接口数据、不是 vendor 二进制"。→ 我们复用时的合规姿势与此相同（本项目 S5KJN1 已经在用 vendor 模式表）。

### 3.2 MediaTek 官方树：多机型 IMX596 驱动（独立交叉验证）

GitHub code search `filename:imx596` 命中 250+，`imx596 path:drivers/misc/mediatek/imgsensor` 命中 268。典型路径：

```
drivers/misc/mediatek/imgsensor/src-v4l2/common/<机型>imx596_mipi_raw/
    ├── <机型>imx596mipiraw_Sensor.c     ← 完整驱动 + 全部 mode 表
    ├── <机型>imx596mipiraw_Sensor.h
    ├── <机型>imx596_eeprom.c / .h
    └── <机型>imx596_ana_gain_table.h
```

出现机型前缀：`rubens / matisse / plato / aristotle / rembrandt / yuechu / corot`（对应 Xiaomi MT6895/MT6983/MT6985 一批机器）。可直接下载的仓库举例：

- <https://github.com/xiaomi-mediatek-devs/android_kernel_xiaomi_mt6895>（branch `lineage-22.1`）
- <https://github.com/XagaForge/android_kernel_xiaomi_mt6895>
- <https://github.com/AdarshGrewal/android_kernel_xiaomi_zircon>

从 `rubensimx596mipiraw_Sensor.c`（58 901 B）实测提取到的硬参数：

```
L183: .mipi_lane_num  = SENSOR_MIPI_4_LANE,
L184: .i2c_addr_table = {0x20, 0xff},        // 8-bit 写地址 0x20 ⇒ 7-bit 0x10
L66 : #define SENSOR_ID_ADDR  0x0016
L190: { 5184, 3904, ... }                    // Preview/全尺寸
L516: write_cmos_sensor_8(ctx, 0x0100, 0x01) // stream on
```

→ **这与 nixos 表完全同构**（同一颗芯片的两份独立实现），可用来校验我们搬运的表有没有抄错。

### 3.3 主线 Linux：没有 imx596；近亲是 CCS 风格的 imx576

`torvalds/linux` `drivers/media/i2c/` 下的 `imx*`（master，实测列举）：
`imx111 208 214 219 258 274 283 290 296 319 334 335 355 412 415 471 576 678` —— **无 imx596**。

其中 **`imx576.c`** 值得注意（2026 年新增，Silicon Signals）：

- 24 MP Sony 前摄、**4 data lane**、10-bit、`IMX576_CHIP_ID 0x0576`
- 但它走 **MIPI CCS 抽象层**：`CCS_R_EXTCLK_FREQUENCY_MHZ`、`CCS_R_CSI_DATA_FORMAT`、`CCS_R_CSI_LANE_MODE`、`ccs_pll` 计算
- **在 `v6.17` tag 上是 404，仅 `master` 有** → 本项目 6.17-rc1 内核里没有，要用需 backport

**为什么它相关**：IMX596 的核心控制寄存器（`0x0016` model id、`0x0340` frame length、`0x0342` line length、`0x0202` exposure、`0x0204` gain、`0x0100` mode select）**恰好都是 MIPI CCS 标准寄存器**。但 IMX596 的 vendor init 表里还含大量非 CCS 的 Sony 私有块（`0x0136/0x0137` INCKSEL、`0x5c00`、`0x6100`、`0x6200`、`0x9200`、`0xa100`…），所以**不能**直接丢给通用 `ccs` 驱动自动探测。→ 结论：imx576 只能当"骨架参考/备选"，不是首选。

### 3.4 已排除的树（复核）

- `MiCode/Xiaomi_Kernel_OpenSource`（`liuqin-t-oss`）：只有 imx214/219/258/274/290/319/355，无 techpack/camera（旧文档已确认，本次未再变）。
- `LineageOS/android_kernel_xiaomi_sm8450`：只有 `techpack/stub`。
- 本项目内核 `yzddmr6/linux-sm8450-liuqin`（`liuqin-6.17`）：`drivers/media/i2c/` 实测只有 `s5kjn1.c` 与主线那批 `imx*`，**无 imx596.c**。

## 4. IMX596 器件参数

| 项 | 值 | 等级 | 来源 |
|---|---|---|---|
| 有效像素 | **5184 × 3904**（20.24 MP） | 【确认】 | MTK `imgsensor_info` + nixos `imx596_modes[0]` |
| 最大链路 | 4 data lane（D-PHY） | 【确认】 | 两处独立一致 |
| I2C 从地址 | **7-bit `0x10`**（vendor 8-bit 写地址 `0x20`） | 【确认】 | MTK `i2c_addr_table={0x20}`；nixos `reg = <0x10>` |
| Sensor ID | `0x0016` 读出 `0x0596` | 【确认】 | nixos `chip_reg/chip_id` |
| MCLK | 19.2 MHz（`CAM_CC_MCLK5_CLK`） | 【确认】 | nixos DT `assigned-clock-rates = <19200000>` |
| Link frequency | **678.4 MHz**（= 1356.8 Mbps/lane） | 【确认】(他人实测) | `CAM_START_PHYDEV` datarate 1356800000 |
| Bayer 顺序 | **BGGR**（10-bit） | 【确认】(他人实测) | 红目标出蓝的实测 + vendor HAL 表 |
| 曝光寄存器 | `0x0202`（16-bit） | 【确认】 | 两处一致 |
| 模拟增益 | `0x0204`，范围 0…1008，Sony 码 `code = 1024 − 1024/gain`（0=1x，1008≈64x） | 【确认】 | nixos desc + `imx596.yaml` + libcamera helper |
| VTS | `0x0340` | 【确认】 | 两处一致 |
| Stream on | `0x0100`（bit0=1） | 【确认】 | MTK `0x0100=0x01`；nixos 16-bit `0x0103` |
| 光学黑电平 | 64 @10-bit（4096 @16-bit） | 【确认】(他人实测) | `imx596.yaml` |

> **注**：前摄与后摄 S5KJN1 的 I2C 地址**同为 `0x10`**。这正是必须把前摄挂在 CCI master0、后摄挂在 master1 的原因——两条独立总线，否则地址冲突。

## 5. 骨架选型

| 候选 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **本项目 `s5kjn1.c`** | 同代码基、同 camss 版本、已在本机出图；`V4L2_EVENT`/runtime PM/regulator 写法现成 | 需换表、换 chip id、改 lane/bus code | **首选骨架（方案 A）** |
| `qcom-liuqin-sensors.c`（nixos） | 表驱动、imx596+sc202cs 现成、注释带踩坑 | 与本项目 s5kjn1 驱动结构不同，整包替换风险大；1629 行 GPL 补丁需裁剪 | **只取表，不取框架** |
| 主线 `imx576.c` | 上游风格、CCS、4-lane、同代 Sony | 6.17 没有；CCS 抽象与 vendor 私有块不兼容 | 备选（方案 C） |
| 主线 `imx258.c` / `imx355.c` | 经典 Sony CCI 驱动、`0x0136/0x0137` 同族写法 | 老一代、无 4-lane 高分辨率模式 | 不推荐（不如 s5kjn1.c） |

**结论**：`imx596.c` = 复制 `s5kjn1.c` 的骨架 + 换 §4 的参数 + 贴 §3.1 的两张表。

## 6. vendor `.bin` 提取：格式实测与更正

> 这一节纠正旧文档 §"唯一可行的深挖路线"里的方法性错误。**结论：这条路可行但不是必须，而且不能用 readelf。**

### 6.1 结论先说

1. `com.qti.sensormodule.*.bin` **不是 ELF**，是 Qualcomm 的 **Chromatix 参数容器**；`readelf`/`objdump` 找不到 `.rodata`。
2. 表**不是**裸 `uint16` 序列，不能靠"扫连续 (reg,val) 对"直接捞出来——本次用启发式扫描（4/8 字节步长、大小端、3 种编码）在真实样本上 **0 命中**。
3. 已有公开工具能解开它：`fractalawareness/SensormoduleTool`。
4. **对本项目而言不必做**：init/mode 表已在 §3.1、§3.2 两处公开可取。提取降级为"交叉校验"。

### 6.2 实测证据（样本：`com.qti.sensormodule.semco_imx586.bin`，461 416 B）

```
magic      = b'QTI Chromatix Heade'          ← ASCII，非 ELF（\x7fELF 检查为 NOT ELF）
u32 @0x1c  = 0x70a68                          ← = 461416 = 文件长度
u16 @0x20  = (1, 1)                           ← 版本 1.1
@0x28      = b'Parameter 3.'
header strings: ['QTI Chromatix Header', 'Parameter 3.', '1 (1807311300)',
                 'sensorDriverData', 'cameraModuleData', 'flashDriverData', 'actuatorDriver']
```

→ 容器 = **magic + 总长度 + 版本 + 参数目录**，寄存器表在 `sensorDriverData` 这个参数块内部。

工具的 `.ini` 反映了它需要**逐模组标定的偏移**：

```ini
VarSizeA=2      LineSkipA=39    RegStartA=502D8   RegSizeA=2340
ResCapStart=4D6E0
RelativeLineL=0 RelativeFrameL=8 RelativePixelClockInd=20 RelativeBinInd=28 ...
```

它的解码输出（`res0.txt`，IMX586 全尺寸模式）正是我们要的形态：

```
ResWidth=8000  ResHeight=6000  LineL=9441  FrameL=6079  PixelClock=1259960000
0x0112 = 0x0a   0x0113 = 0x0a   0x0114 = 0x02
0x0342 = 0x24   0x0343 = 0xe0        ← line length
0x0340 = 0x17   0x0341 = 0xbf        ← frame length 6079
0x034c..0x034f = 0x1f40 × 0x1770     ← 8000×6000
0x0301/0x0303/0x0305/0x0307/0x030d   ← PLL
0x0202/0x0203, 0x0204/0x0205         ← 曝光 / 增益
0x0900 = 0x00   0x0901 = 0x11        ← binning
```

注意 `0x0112`、`0x0113` 是**逐字节写**的 —— 这与 MTK 驱动 `write_cmos_sensor_8` 和 nixos `CCI_REG8` 的写法完全对应。

### 6.3 若仍要提取（三步，按可靠性排序）

**路线 1（最省事，推荐）：直接用现成的两份表**
不需要碰 `.bin`。见 §3.1 / §3.2。

**路线 2：用 SensormoduleTool 的偏移法**
```bash
git clone https://github.com/fractalawareness/SensormoduleTool
# 用 .ini 里的 RegStartA/RegSizeA/ResCapStart + Relative*Ind 定位
# 输出形如 "0x0340 = 0x17" 的 reg=val 列表
```

**路线 3：自己写定位器（容器无关）**
```bash
# 1. 从 ROM 里拿出 .bin（需要先处理 Android sparse super.img）
#    先确认 magic，再看 0x1c 处长度字段是否等于文件长度
head -c 64 com.qti.sensormodule.liuqin_aac_imx596_front_i.bin | xxd
# 2. 解析参数目录，进入 sensorDriverData
# 3. 在 sensorDriverData 内以"每模式记录"为单位扫：
#    - 头部应出现 0x0136/0x0137（Sony INCKSEL），可用作锚点
#    - 紧接着找 0x0340/0x0342（VTS/line length）自校验
#    - 用 0x034c/0x034d 解出的宽高必须等于 5184×3904 来验证窗口正确
# 4. 校验：解出的 PLL/hts/vts 应与 §4 表一致
```

**判定锚点（重要）**：Sony 表的特征是开头 `0x0136 = 0x13`、`0x0137 = 0x33`（nixos 表实测前两条），然后 `0x0101`、`0x32c8`… 用这个当指纹比"扫 uint16 对"可靠得多。

## 7. DT 侧方案

### 7.1 本机实测现状（只读命令，2026-10-27）

```
=== cci nodes ===
FOUND /proc/device-tree/soc@0/cci@ac15000     i2c-bus@0  i2c-bus@1
--- i2c-bus@0 ---            ← 无 status 属性、无 camera 子节点
--- i2c-bus@1 ---  okay  camera@10          ← 后摄 S5KJN1
=== i2c adapters ===  7-0010  ← 即 s5kjn1(0x10)，总线号每次启动漂移
=== media0 ===
entity 7 : msm_csiphy2 … -> "msm_csid0":0 []        ← 存在，未接 sensor
entity 10: msm_csiphy3 … -> "msm_csid0":0 [ENABLED] ← 当前唯一在用的 PHY
=== camss ports in DT ===   port@3   data-lanes = 0 1 2 3
=== i2c module dir ===  s5kjn1.ko        ← 只有后摄驱动
```

**结论**：前摄所需的一切（CCI master0、CSIPHY2 实例）在硬件/驱动层**已经就绪**，缺的只是 DT 节点 + sensor 驱动。

### 7.2 DT 草案（基于 nixos 已验证节点，标注待核对项）

```dts
/* 前摄：CCI0 master0 / CSIPHY2 / MCLK5 / RESET GPIO127 */
&cci0_i2c0 {
	camera@10 {
		compatible = "sony,imx596";
		reg = <0x10>;				/* vendor 8-bit 写地址 0x20 */
		orientation = <0>;			/* front，libcamera Location 用 */
		clocks = <&camcc CAM_CC_MCLK5_CLK>;
		clock-names = "xvclk";
		assigned-clocks = <&camcc CAM_CC_MCLK5_CLK>;
		assigned-clock-rates = <19200000>;	/* 19.2 MHz */
		reset-gpios = <&tlmm 127 GPIO_ACTIVE_LOW>;
		pinctrl-names = "default", "sleep";
		pinctrl-0 = <&cam_sensor_mclk5_active &cam_sensor_active_rst5>;
		pinctrl-1 = <&cam_sensor_mclk5_suspend &cam_sensor_suspend_rst5>;
		vddd-supply  = <&camera_front_vdig_ldo>;	/* ← 供电标签需按本 dts 核对 */
		vdda-supply  = <&camera_front_avdd_ldo>;
		vddio-supply = <&pm8350c_l1>;
		status = "okay";

		port {
			imx596_out: endpoint {
				clock-lanes = <0>;
				data-lanes = <1 2 3 4>;	/* sensor 侧 1-based 编号 */
				link-frequencies = /bits/ 64 <678400000>;
				remote-endpoint = <&camss_in2>;
			};
		};
	};
};

/* pinctrl：MCLK5 = gpio105，RESET5 = gpio127 */
cam_sensor_mclk5_active: cam-sensor-mclk5-active {
	pins = "gpio105"; function = "cam_mclk";
	drive-strength = <4>; bias-disable;
};
cam_sensor_mclk5_suspend: cam-sensor-mclk5-suspend {
	pins = "gpio105"; function = "cam_mclk";
	drive-strength = <4>; bias-pull-down;
};
cam_sensor_active_rst5: cam-sensor-active-rst5 {
	pins = "gpio127"; function = "gpio";
	drive-strength = <4>; bias-disable;
};
cam_sensor_suspend_rst5: cam-sensor-suspend-rst5 {
	pins = "gpio127"; function = "gpio";
	drive-strength = <2>; bias-pull-down;
};

/* camss 侧：新增 port@2（当前 dts 只有 port@3） */
&camss {
	ports {
		port@2 {
			reg = <2>;
			camss_in2: endpoint {
				clock-lanes = <4>;	/* 注意：camss 侧 0-based */
				data-lanes = <0 1 2 3>;
				remote-endpoint = <&imx596_out>;
			};
		};
	};
};
```

### 7.3 DT 参数确认状态

| 参数 | 值 | 状态 |
|---|---|---|
| I2C 地址 | `0x10` | 【确认】MTK `0x20`(8-bit) + nixos `reg=<0x10>` |
| CCI 总线 | `cci0_i2c0`（master0） | 【确认】厂商 dtbo `cci-master=0` + 实机 `i2c-bus@0` 空置 |
| MCLK | `CAM_CC_MCLK5_CLK`，19.2 MHz | 【确认】厂商 `CAMIF_MCLK5` + nixos |
| RESET | `&tlmm 127`（GPIO_ACTIVE_LOW） | 【确认】厂商 dtbo 两个 gpio 为 `0x69`=105、`0x7f`=127；nixos 取 127 作 reset |
| MCLK GPIO | `gpio105`（功能 `cam_mclk`） | 【确认】两处一致 |
| data-lanes | 4 lane | 【确认】 |
| link-frequency | 678 400 000 | 【确认】(他人实测) |
| **CSIPHY 编号** | **2**（`port@2`） | **【待测】冲突：厂商 dtbo 解出 `csiphy-sd-index=3`** |
| 供电 rail 标签 | vddd/vdda/vddio（nixos）vs `cam_vana`+`cam_clk`（厂商 dtbo） | **【待测】** 厂商只列 2 条轨，nixos 用 3 条；必须与本项目 dts 的 regulator 标签 + 实际上电时序对齐 |
| CSIPHY lane 表 | vendor 2.1.3 | **【待测】** 见 §10 风险 R1 |
| 是否需要 EEPROM 节点 | 有 EEPROM（`/persist/camera/`） | 【推测】非必需，先不接 |

> **CSIPHY 编号冲突怎么处理**：本项目实机证据很强——**只有一个 `port@3`，且 `msm_csiphy3` 是唯一 ENABLED 链路**，说明后摄在 CSIPHY3。若前摄真是 CSIPHY3 就会与后摄撞车，因此前摄只能在 CSIPHY2/0/1 之一。nixos 选 `port@2` 且声称实测出图，**先照抄 port@2**；若 probe 后无数据，改成 `port@1`/`port@0` 各试一次（每次只改 1 行 + `port@N` 的 `reg`，重编 dtb 约 1 分钟）。

## 8. 用户态还需要什么（libcamera）

本项目用 libcamera `simple` pipeline + 软 ISP，所以除了内核驱动还要两小件：

1. **`CameraSensorHelperImx596`**（`src/ipa/libipa/camera_sensor_helper.cpp`）
   ```cpp
   class CameraSensorHelperImx596 : public CameraSensorHelper {
   public:
       CameraSensorHelperImx596() { gain_ = GainType::Sony; }   // 等价实现
       double gain(uint32_t c) const override { return 1024.0 / (1024.0 - c); }
       uint32_t gainCode(double g) const override { return 1024.0 - 1024.0 / g; }
   };
   REGISTER_CAMERA_SENSOR_HELPER("imx596", CameraSensorHelperImx596)
   ```
   依据：`0007-sensor-helpers.patch` 实测内容 + `imx596.yaml` 注释"Sony-style code 1024 − 1024/gain"。

2. **tuning yaml**：`blackLevel: 4096`（16-bit 标度）、`Awb.max-gain: 1.6`、identity CCM（三色温点）。可直接抄 `pkgs/libcamera-af/tuning/imx596.yaml`。

3. `orientation = <0>` 已在 DT 草案里；若驱动不实现 `v4l2_fwnode_device_parse`，libcamera 会报 `Failed to retrieve the camera location`（nixos 文档明确列为 open item）。

| 方案 | 做法 | 工时 | 风险 | 适用 |
|---|---|---|---|---|
| **A. 搬表 + 复用 s5kjn1.c 骨架** | 新建 `imx596.c`，贴 §3.1 的表，DT 加节点，libcamera 加 helper | **0.5–1 天** | 中低 | **推荐** |
| B. 整包移植 `qcom-liuqin-sensors.c` | 用 nixos 驱动替换/并列，同时接 SC202CS | 1.5–2 天 | 中（与现有 s5kjn1 驱动并存/DT 冲突） | 想一次做完三摄 |

**方案 A 的落地步骤**

1. `cp drivers/media/i2c/s5kjn1.c drivers/media/i2c/imx596.c`
2. 换：compatible → `sony,imx596`；chip id 校验 → `0x0016/0x0596`；lane=4；bus code `SBGGR10_1X10`
3. 贴 `imx596_init`（~365 条）+ 4 个 mode 表 + `link_freq_menu`
4. **`stream_on` 用 16 位写** `0x0100 = 0x0103`（坑 1）
5. DT 加 §7.2 节点；`Kconfig`/`Makefile` 加 `CONFIG_VIDEO_IMX596`
6. 重編内核 + dtb（本项目已有构建流程），`modprobe imx596`
7. 验证：`media-ctl -p` 出现 `imx596`；`v4l2-ctl --list-formats-ext` 有 5184×3904
8. 出帧：`cam --stream role=raw --capture=1 --file=/tmp/f.raw`；前摄全尺寸 5184×3904 的 raw10 帧约 **25.3 MB**（行 6480 B × 3904），与后摄当前 3840×2160 的 10 368 000 B/帧 不同，别拿后摄的数字当基准

## 10. 风险表

| ID | 风险 | 影响 | 概率 | 缓解 |
|---|---|---|---|---|
| **R1** | 本项目 camss 用的 CSIPHY lane 表与 vendor 2.1.3 不同，CSIPHY2 失谐 | 能推流、收不到数据（nixos 踩过两次：link freq 与 lane 表） | 中 | 先复现 nixos 的 `lane_regs_sm8475`（vendor 2.1.3 表，patch 内 `camss-csiphy-3ph-1-0.c`） |
| **R2** | CSIPHY 编号不是 2 | probe 无 v4l2 subdev 或 timeout | 中 | 依次试 port@2/1/0，每次 1 行 |
| **R3** | stream-on 写宽度搞错 | 无声失败（最坑） | 中 | 用 16 位 `0x0103`；对照 MTK 的 8 位写法 |
| **R4** | 供电 rail 标签/电压不对 | probe `-110`/`-ETIMEDOUT` | 中 | 先量/后改；nixos 明确"任何代码都不写轨道电压" |
| **R5** | 单消费者限制：三摄共享 `csid0 → vfe0_rdi0` | 同时开两路都不出帧 | 已确认 | `media-ctl -r -d /dev/media0` 复位；一次只用一颗 |
| **R6** | 搬运表抄错 | 花屏/不启动 | 低 | 用 MTK 表交叉比对（§3.2） |
| **R7** | 寄存器表许可 | 若将来 upstream 会被质疑 | 低（自用无碍） | 与 S5KJN1 同姿势；必要时做成 operator payload |

## 11. 可行性结论

**能做。** 理由：

1. **不是从零开始**：同一台机器（liuqin）已有别人做完的 mainline 实现，含 DT、驱动、tuning、libcamera helper，且记录了 3 个真实坑位。
2. **寄存器表有双份独立来源**（Qualcomm 提取 + MediaTek 官方），可互相校验，逆向 vendor `.bin` 从"关键路径"降级为"可选校验"。
3. **驱动骨架现成**：本项目 `s5kjn1.c` 与目标同代码基；camss 已支持 sm8475（实机 media graph 可证）。
4. **DT 侧只差一个节点**：CCI master0 与 CSIPHY2 实例都已存在。

**时间**：方案 A 0.5–1 天（含一次内核构建 + 上机调试）；主要不确定性在 CSIPHY 编号与 lane 表（R1/R2），最坏情况多花半天做试错。

**最大风险**：CSIPHY 通道/时序不匹配导致"STREAMON 成功但一帧都收不到"——这是这类移植的典型失败模式，nixos 的文档里两次都是这个症状，且都定位到了具体原因（link freq 678.4 MHz、16 位 stream-on、vendor 2.1.3 lane 表），所以有明确的排查路径，不是黑盒。

**不建议**走"逆向 `.bin` → 手写驱动"的老路线：既慢（旧估计 12+ 小时），方法本身也不成立（§6）。
